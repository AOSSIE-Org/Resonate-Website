## Notes

### Note 1: Inline redirect script on the bare `/` route — `src/app/(root)/page.tsx:19`

- Category: design-tradeoff
- Observation: The root page renders `<script dangerouslySetInnerHTML={{ __html: \`location.replace(${JSON.stringify(defaultLocalePath)})\` }} />`. This is an inline script that navigates the browser to `/en` as soon as the parser reaches it. The inserted value is the compile-time constant `"/en"`, built from the `Locale`-typed `defaultLanguage` in `src/config/languages.ts` and serialized with `JSON.stringify`. No request data can reach it, so it is not an XSS or open-redirect vector. Its only security-relevant effect is that any Content Security Policy added to the site later (for example via `<meta http-equiv="Content-Security-Policy">`, since GitHub Pages cannot send headers) must allow this inline script by hash or `'unsafe-inline'`. Otherwise the JS redirect is blocked and only the slower meta-refresh fallback runs.
- Rationale: This is deliberate and documented. `AGENTS.md` (Project Boundaries, "Root route") specifies the inline `location.replace("/en")` with a meta-refresh and `<noscript>` link as no-JS fallback, and forbids `redirect()` because it exports an empty error page. The comment block at `src/app/(root)/page.tsx:7-11` explains that a static export cannot send HTTP redirects and that a meta refresh alone showed a blank page on first visits. Removing the inline script would contradict that stated design.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations**

- `node_modules/`, `.next/`, `out/`, `package-lock.json` and binary assets (images, fonts, `.ico`, `.webp`, `.png`) were out of scope and not reviewed. Dependency versions were not checked against advisories, and the built `out/` HTML was not inspected, so any issue introduced only at build time by Next.js, `next-intl` or other dependencies is not covered.
- GitHub repository settings that affect workflow risk (branch protection, environment protection rules on `github-pages`, the default `GITHUB_TOKEN` permission setting, fork-PR approval policy) are external state and could not be evaluated.
- Hosting-level controls (GitHub Pages TLS, custom domain and DNS configuration for `resonate.aossie.org`, response headers) are infrastructure outside the repository and were not evaluated.
